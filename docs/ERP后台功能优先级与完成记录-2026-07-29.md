## 状态口径

- `✅ 已完成（本地 Mock）`：本地 Web 可以实际点击，数据会在当前 Mock 进程中发生状态变化；刷新开发服务后演示数据会重置。
- `🟡 部分完成`：只完成了该功能的一部分，不能代表表格描述的完整业务已经交付。
- `🔎 待核验`：Excel 原表标记“已建成”，但本轮尚未逐项验证真实接口、状态机和数据持久化。
- `⬜ 未开始`：Excel 原表为规划中或新提议，本地尚未实现。
- `⏸ 范围外`：属于小程序或独立端，本轮明确不修改。
- `🧪 待用户测试`：开发侧已完成本地验证，等待使用方按“测试入口”实际操作。
- `✅ 用户已测试`：只有收到使用方明确反馈“测试通过”后才标记，并同时填写测试日期。

> 注意：Excel 中的“✅已建成”是原清单状态，不等于当前仓库已经达到生产可用。本仓库交接文档说明，除客户、合同、收款、订房、入住主链外，很多页面仍属于 Visible、Schema-faithful 或 Mock。

### 智能排房需求来源与确认边界

1. **Excel 已确认的内容**：F019 的目标是“系统按客户要求自动推荐排哪间房，替店长动脑挑房间”；Excel 没有给出评分权重、换房次数、付款门槛或特殊客群规则。
2. **旧 ERP 采集证据**：原仓库保存了旧 ERP 的菜单名“智能排房”和旧页面地址 `Page/GuestRoomManger/BrainpowerHouseList.aspx?navid=517`。字段蓝本还记录了分店、入住日期、天数、退房日期、房间类型、楼层，但同一条记录混入了服务预约列，说明自动采集结果存在噪声，只能作为参考，不能直接当甲方确认的 PRD。
3. **`qidefenfang-info` 历史实现**：GitHub 中确有可运行过的 `RoomAssign.vue`、`RoomGantt.vue` 和 `roomAssignService.ts`。历史算法是“排除日期区间冲突 → 同房型优先 → 价格升序 → 楼层排序”，并实现预订、入住、退房、取消和并发防重复预订。该算法属于开发实现，不是甲方书面确认的评分规则。
4. **会议纪要明确的问题**：2026-03-04 会议纪要指出旧智能排房“半自动化、操作复杂、无法直观显示未来入住情况”。因此未来档期时间轴是明确改善方向；当前 14/30/60/90 天网格和试运行匹配度是开发实现，具体评分权重仍不是会议确认结论。
5. **当前实现的暂定策略**：同门店、入住区间、房型、楼层过滤；排除维修/脏房和日期冲突；连续入住同一房间优先；没有连续房时最多拼接两间房、换房一次；只有合同已审核、至少一笔收款已审核且未订房的客户可选择。2026-07-30 增加房源完整度卡片和可解释推荐理由。以上属于本轮业务设计，不是从 GitHub 完整需求文档原样复制。
6. **上线前必须由甲方确认**：锁房最低付款金额或比例、是否允许换房、房型能否降级/升级、楼层和朝向偏好、双胎/多胎及医疗特殊需求、保洁/维修缓冲时间、超卖处理、推荐结果的人工调整权限。

### 智能排房开源借鉴结论（2026-07-30）

- GitHub 暂未找到成熟、可信且可直接商用的“月子会所 Web ERP”开源项目。后续不以低质量同名仓库作为业务依据，改为借鉴酒店预订、医疗床位和资源预约领域的成熟设计，再结合甲方流程自行实现。
- **OpenMRS Bed Management**（https://github.com/openmrs/openmrs-module-bedmanagement）：可借鉴“门店/区域/房间/床位类型/标签/布局/入住位置”的主数据关系和 REST API 边界；许可证为 AGPL-3.0，不直接复制代码进入当前客户项目，只借鉴领域模型。
- **vis-timeline**（https://github.com/visjs/vis-timeline）：支持时间范围、缩放、拖动和编辑，许可证为 MIT 或 Apache-2.0 二选一，适合评估为14/30/60天房态时间轴组件；正式引入前仍需做 Vue2 兼容、性能和依赖体积验证。
- **Shelf.nu**（https://github.com/Shelf-nu/shelf.nu）：可借鉴跨地点资源预约、防重复预订、层级位置、维护提醒和审计日志；许可证为 AGPL-3.0，当前只借鉴产品思路。
- **GSTC**（https://github.com/neuronetio/gantt-schedule-timeline-calendar）：交互上适合房间行+日期轴、多条预订、拖拽和缩放，但完整商用需要商业许可；当前只作为交互参考，不纳入项目依赖。
- 建议路线：优先使用现有 Vue2 组件自行实现房态网格，或先做 `vis-timeline` 技术验证；不要为追求“看起来像原系统”而引入授权不清或与现有技术栈不兼容的整套源码。

#### 从资料中确认的核心业务规则

1. **签单到入住前**：建立客户服务群并持续产前跟踪；入住前一周由销售核对出院、接车、用品和身体情况，并把信息同步护理、客房等部门。
2. **入住准备**：客房部根据已预订房型和套餐备房，完成卫生消毒、设备检查、物品配置；客房主管每天查看出入所派工和房态图，客户量大时应提前一天备房。
3. **入住放行**：现有《黄河路店入所服务全流程》写明，家属入住当天在前台办理手续并“交清余款和入住押金”。所以当前“有一笔审核收款即可订房”只能作为锁房临时条件，不能直接等同于允许入住；正式版还要增加余款、押金和放行审核。
4. **入住后任务**：24 小时内完成客房宣教和房内资产核对；护理部完成母婴二分体入所评估；入住第 5/15/25 天做满意度调研；退房前核对房内物品。
5. **套餐主数据**：2026-07-29 收到甲方聊天截图及《奇德芬芳母婴俱乐部·修养套餐价目表》，确认基础套餐、修养套餐B、修养套餐A、精致尊享B、精致尊享A、臻享套餐VIP3楼、至尊套餐VIP5楼共7类，每类均有28/35/42/56天，并分别给出原价、活动价、成交价。价格已录入联调目录；适用门店按聊天中的“中心店”映射到中心广场旗舰店，价格生效日期和多数套餐适用房型仍待甲方确认。
6. **客户意向 A-E**：会议纪要只明确“A 类（高价值）客户”的重要判断因素是首次到店成交率，并要求建立可量化标签；没有定义 B、C、D、E。当前页面展示的“A 近期可签约、B 比较方案……”属于开发暂定口径，不是甲方文件结论，必须向甲方确认或改为可配置字典。
7. **预约**：GitHub 历史实现只证明“项目、时间必填，可关联客户、服务人员和状态”，不能证明完整容量、房间/设备资源或跨项目冲突规则。当前 Web 的人员时段冲突是合理守卫，但参观预约、产康服务预约、到店接待和客房服务预约应拆分业务类型。
8. **品控与 BOM**：品控原表实际包含总经办、企划、销售、护理、产康、膳食、客房 7 个部门及月度汇总，不是升级计划所写的 6 个部门；其中工作表名“客服部”而表内写“客房部”，导入前须甲方确认。产品配料表共有 128 行，属于项目耗材原始数据，但含科研美容项目，不能不分类地直接导入月子 Web ERP。

### 本周能否上线

结论：**可以争取上线一个“内部试运行版 Web ERP 端口”，不能承诺 71 项全部生产完成，也不能在未验收时直接作为正式经营系统切换。**

内部试运行版范围：

1. 客户建档 → 合同审核 → 收款审核 → 订房/入住主链。
2. 服务预约：未来日期、门店/服务人员、时段格式和同一服务人员时段冲突校验。
3. 智能排房：按门店/房型/楼层查询，优先连续空房，找不到时推荐最多一次换房。
4. 房态图：查看房间、预订、入住、维修/脏房占用情况。
5. 卡项与余额继续用于业务验收；支付配置和微信/短信等外部消息通道在接入真实服务前不出现在正式导航中，顶栏站内业务通知独立开放。

- [ ] 甲方确认“锁房付款门槛”（任意已审核首款、固定定金、付款比例或全款）。

- [ ] 配好服务器、域名/HTTPS、数据库备份、日志、故障回滚和初始管理员改密。
- [ ] 使用方按本文测试入口签字确认；未确认项继续标记“待用户测试”。

### 2. 入住天数不是全国统一的法定套餐天数

- 当前有效的月子会所场所标准是 [GB/T 33855-2017《母婴保健服务场所通用要求》](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=3704B7A0367D153A9578E3CC3B39AF30)。
- [GB/T 33855-2026《母婴保健服务机构通用要求》](https://std.samr.gov.cn/gb/search/gbDetailed?id=49FD1852CB08C31FE06397BE0A0A1304) 已发布，将于 2026-08-01 实施并替代 2017 版；当前日期 2026-07-29，尚未生效。
- 国家卫健委《孕产期保健工作规范》中的“产后 42 天”是孕产期健康管理和检查节点，不等于月子中心必须入住 42 天。月子中心入住几天应由套餐和合同约定。
- 本地页面提供 `28/42/56 天`快捷按钮，只作为市场常用商品配置，不能宣传为国家强制标准；最终仍以甲方批准的套餐主数据和客户合同为准。

### 3. 套餐名称必须明确，正式数据需要甲方确认

仓库已有套餐管理字段设计，包括套餐名称、门店、套餐类型、入住天数、房型、参考价、销售价、有效期和权益明细；交接文档同时注明正式价格和权益数据仍待业务复核。因此本轮采用以下口径：

- 套餐名称改为合同必填项。
- 页面先提供待确认的套餐目录用于流程验收；正式启用前必须由甲方确认并由管理员维护套餐主数据。
- 若纸质合同已有正式套餐名，可直接按合同原文录入，但不能自动推断它包含哪些护理、餐食、产康、摄影或赠送权益。
- 套餐天数、入住日期范围、参考价、成交价必须彼此一致；折扣仅作为计算结果，不代替价格审批。

甲方需要书面确认的套餐主数据：

1. 每个门店的套餐名称、版本号、适用房型和上/下架日期。
2. 标准入住天数，以及延住、提前离店、待产占房和宝宝留院时如何计费。
3. 标准价、最低成交价、折扣审批层级、定金规则和退款/违约规则。
4. 套餐内母婴护理、月子餐、产康、摄影、耗材、赠品的次数、金额、有效期及能否转让。
5. 换房、跨店、升级/降级、双胎/多胎、家属陪住和超员的补差规则。

正式预付式服务合同还应明确服务内容、价款、履行期限、退款方式和违约责任，不能只保存一个模糊套餐名称。

### 4. 合同收款和财务审核流程

```text
合同已审核
  → 登记收款（合同首付 / 合同尾款 / 定金 / 其他收款）
  → 待财务审核
  → 财务审核通过并入账
  → 合同已收金额、欠款同步更新
  → 满足订房条件
```

本地已落实：

- 只能给已审核合同登记收款。
- 页面同时显示合同金额、已收金额、待审核金额、本次最多可收金额。
- 新收款不得超过 `合同欠款 - 尚未审核的收款`，防止重复登记和超收。
- `其他收款`必须填写用途；历史收款必须填写补录原因。
- 只有财务点击审核后才计入合同已收金额；单纯登记不等于入账。
- 客户、合同、收款和订房列表均按当前选择门店显示，跨店记录不会混在一起。
- 收款原始凭证、经办人与审核人的职责分离，是后续接入真实后端时必须保留的审计要求。

仍需甲方确认：

1. “定金”和“合同首付”是否为两个财务科目，定金能否自动转首付款。
2. 审核角色是门店财务、总部财务还是分级审核；登记人能否审核自己的收款。
3. 支持哪些支付方式、是否强制上传水单/支付流水号、现金如何日结。
4. 多收、错收、撤销、退款、冲红、坏账和跨合同转款的审批流程。
5. 发票在收款时、入住时还是结清时开具。

### 5. 收款到订房的同步条件

本地临时规则按当前需求执行：合同已审核、至少一笔收款已经财务审核且金额大于 0、当前没有有效订房，并且合同门店与当前门店一致时，才进入订房候选。财务审核完成后：

- 尚未订房：系统自动切换到订房页并带入该合同。
- 已有订房：系统切换到该合同门店并展示现有订房，不重复生成。
- 不同门店：不会出现在当前门店的合同、收款或订房候选中。
