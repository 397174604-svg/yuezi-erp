### 1.2 高频板块的阶段性判断

| 排名 | 模块 | 判断 | 依据 |
| --- | --- | --- | --- |
| 1 | 护理管理 | 业务记录写入频率最高 | 在住期间按妈妈、宝宝、班次、护理项目持续产生记录；护理中心有 20 项实时统计、17 个子页面和 9 个客户快捷业务入口 |
| 2 | 客房管理 | 实时查看与跨部门协同频率最高 | 房态图是销售、客服、护理、客房和管理层共同入口；订房、入住、续住、换房、退房、清洁连续改变占用状态 |
| 3 | 客户管理 | 前台获客与客服使用频繁 | 线索、客户、跟进、签单、参观、公海、回访、投诉、消息形成完整客户生命周期 |
| 4 | 销售管理 | 单据频率中高、金额影响高 | 合同、商品销售、套餐、卡项、优惠和赠送构成收入来源 |
| 5 | 财务管理 | 点击频率未必最高，但控制风险最高 | 收款、退款、欠款、发票、费用、付款和审核必须与合同及业务单据对账 |
| 6 | 膳食/仓存/产康 | 执行频率高，依赖入住规模 | 每日餐单、送餐和项目服务会持续生成食材、耗材和库存消耗 |

结合实时待办压力，当前实施优先级修正为：

1. 财务对账与审批：待审核收款、合同欠款的存量压力最高。
2. 产康权益闭环：未耗卡提醒数量高，应先打通权益—预约—执行—耗卡。
3. 客房在住协同：作为护理、膳食、产康和退房结算的共同入口。
4. 护理执行：预计日常写入频率最高，但仍需用长期日志统计验证。
5. 仓存事务：最新日志显示当前写入活跃，且一笔业务会产生大量明细日志。

最终“真实使用频率排名”应使用新系统 `operation_log` 按最近 30/90/180 天统计：

```sql
SELECT module_code,
       COUNT(*) AS action_count,
       COUNT(DISTINCT user_id) AS active_users,
       COUNT(DISTINCT DATE(occurred_at)) AS active_days
FROM operation_log
WHERE occurred_at >= CURRENT_DATE - INTERVAL '90 day'
  AND action_type IN ('VIEW', 'QUERY', 'CREATE', 'UPDATE', 'APPROVE', 'PRINT')
GROUP BY module_code
ORDER BY action_count DESC;
```

同时必须把“查询/查看”和“新增/执行/审批”分别排名，否则房态图等看板会掩盖护理记录等真实业务写入。

## 2. 总体架构

建议先采用模块化单体，而不是立即拆微服务：

```text
认证与组织
  ├─ 客户与会员
  ├─ 销售与合同
  ├─ 财务结算
  ├─ 客房与入住
  ├─ 护理与健康
  ├─ 产康服务
  ├─ 月嫂服务
  ├─ 膳食执行
  ├─ 仓存供应链
  ├─ 商城内容
  ├─ 审批与消息
  └─ 报表与审计
```

每个模块独立维护 Controller、Application Service、Domain、Repository 和表前缀；模块之间通过 ID、领域事件和只读查询模型协作，禁止跨模块直接修改对方业务表。

所有业务表统一包含：

```text
id, tenant_id, store_id, created_by, created_at,
updated_by, updated_at, version, deleted_at
```

- 主键建议 UUIDv7 或雪花 ID。
- 金额统一使用 `decimal(18,2)`，禁止浮点数。
- 数量使用 `decimal(18,4)`，支持食材和耗材小数单位。
- 资金、护理、健康、库存流水不得物理删除。
- 核心单据使用 `version` 乐观锁。
- 每个状态变更写入独立状态历史表。

## 3. 组织、账号与权限

### 3.1 核心表

原系统部门页已只读核验到以下结构证据：

- 顶部操作：添加、二维码打印、编辑、删除、同步钉钉。
- 列字段：部门名称、排序、备注、备用字段1、备用字段2、门店、分店类型、部门主管、所属区域。
- 根级组织/门店至少包含：奇德芬芳、中心广场旗舰店、奇德芬芳北京总公司、黄河路轻奢店。
- 这说明原表同时混放了公司、门店和部门。新系统应拆分 `sys_org_unit` 与 `sys_store`，再用 `org_unit_type` 或关联表表达公司—门店—部门关系，不能继续把“门店”仅作为部门的一列文本。

部门使用 `parent_id + path` 保存树结构，例如 `/总部/中心店/护理部`。员工档案与登录账号分离：一个员工可以没有账号，账号必须绑定员工才能参与排班、审批和业绩归属。

### 3.2 四层权限

1. 菜单权限：是否可进入页面。
2. 操作权限：新增、编辑、删除、审核、打印、导出等。
3. 数据权限：本人、本部门、本门店、指定门店、全租户。
4. 字段权限：手机号、证件、健康、金额等是否可见、脱敏、可编辑。

### 5.2 关键约束

- 房间占用不是一个静态状态字段，而是预订、入住、维修、清洁等时间区间的计算结果。
- PostgreSQL 推荐使用排他约束防止同一床位时间重叠。
- MySQL 可使用事务内区间锁和唯一占用日历表 `room_occupancy_day`。
- 换房不是修改 `room_stay.room_id`，而是结束旧的 `room_stay_room_history` 并新增一段历史。
- 退房与结账分离：允许“已退房未结账”。

### 5.3 客房模块优化

1. 房态图按楼层虚拟滚动，只加载当前日期范围和当前门店。
2. 房卡同时显示住户、合同天数、已住/剩余天数、风险、护理等级和欠款标记。
3. 所有跨店订房、换房、维修占用先调用统一的房态冲突检查。
4. 建立 `room_command` 统一承接订房、入住、续住、换房、退房、结账，避免各页面分别修改状态。
5. 建立房态读模型 `room_status_snapshot`，由事件异步刷新，房态图不直接联查十余张业务表。
6. 给客房、销售、护理不同视角：销售看可售与价格，护理看住户与护理等级，客房部看清洁与维修。

### 6.2 记录模型

- `care_plan_item` 是计划模板实例，定义项目、频次、时间窗和适用对象。
- `care_task` 是某天某次真正需要执行的任务。
- `care_execution` 是不可篡改的执行事实，包含执行人、开始/完成时间、结果和异常。
- 生命体征放入 `care_execution_vital`，不要把几十个体征字段塞进任务表。
- 妈妈和宝宝记录共享执行主表，但临床字段分别进入专属扩展表。
- 修正记录采用“原记录 + 更正记录 + 更正原因”，不覆盖原值。

### 6.3 护理模块优化

1. 护理中心从“客户列表”升级为“班次任务中心”：待执行、临期、超时、异常、待交接五个队列。
2. 一次选择客户后，妈妈护理、宝宝护理、产康预约、医生查房等保持同一上下文，减少重复选人。
3. 护理计划按入住日自动展开任务，出院、外出、续住、换房事件自动暂停或重排。
4. 移动端支持床旁扫码或房间码确认，记录实际执行人、时间和设备。
5. 异常/危险标记必须触发升级规则、护士长消息和处置闭环。
6. 交班视图只显示本班新增、未完成、异常和重点观察项，避免重复阅读全部历史。
7. 建立护理质量指标：计划完成率、超时率、异常闭环时长、每客户护理工时、重复记录率。

## 10. 实施顺序

1. 组织、员工、账号、角色、权限、门店、字典及操作日志。
2. 客户 → 合同 → 应收 → 收款 → 订房 → 入住主链路。
3. 房态事件、护理计划/任务/执行与交接。
4. 产康、膳食执行驱动库存消耗。
5. 退款、付款、优惠、派工等通用审批及消息。
6. 日汇总报表、历史迁移、权限核验和金额/库存/房态对账。

## 11. 历史迁移与对账

- 建立 `migration_source_map(source_system, source_table, source_id, target_type, target_id)`。
- 先迁组织和字典，再迁员工/客户，再迁合同/入住，最后迁资金、护理和库存流水。
- 迁移后至少完成四组对账：
  - 客户、合同、入住人数与状态分布。
  - 合同应收、审核收款、退款、欠款与总账。
  - 房间逐日占用无重叠。
  - 库存期初 + 入库 - 出库 = 期末。
- 历史护理记录保留原创建人、原时间和来源标识，不伪装成新系统实时录入。

这些资料确认现有设计还需要增加以下能力：

1. 套餐不是单一价格字段，而是“套餐版本 + 房型 + 天数 + 权益频次 + 赠品 + 可选项目组”的矩阵。
2. 合同签署时冻结价格、权益、赠品和优惠规则快照，后续政策更新不得影响历史合同。
3. 入所前生成资料清单和房间准备清单；入住时分别完成妈妈与宝宝评估。
4. 护理按班次、计划、任务、执行、交接和异常升级建模，而不是只保存记录表。
5. 产康操作标准按版本、阶段和步骤管理；执行完成后确认实际耗材并生成库存流水及项目成本。
6. 品控按标准版本、检查、问题、整改、复查和计分建模，超时任务可自动生成不符合项。
7. 客房补充房间准备、物品交接、门卡、布草、洗衣、维修 SLA 和满意度任务。
8. 员工执行产康项目除菜单权限外，还需校验培训、考核、证书和项目授权有效期。
