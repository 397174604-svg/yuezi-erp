## 0. 给下一位开发者的结论

当前项目已经不是单纯的 Vue 页面 Demo：

- 组织、员工、账号、角色、菜单按钮权限、门店范围和系统配置已进入 MySQL。
- “客户建档 → 合同 → 合同审核 → 收款 → 收款审核 → 智能订房 → 入住”主链路已有真实 API、事务、权限校验和审计。
- 产康、财务、客房、销售已经建立部分真实业务表和操作接口。
- 大量旧 ERP 页面已经完成菜单、工具栏、查询条件、字段和弹窗层面的复刻。
- 但护理、膳食、仓存、商城、月嫂、基础资料、系统设置及部分客户/销售/财务/客房子页仍处于“字段复刻、静态演示或部分交互”状态，不能称为完整后端。

继续开发时最重要的约束：

1. 真实业务必须使用 MySQL，不新增 JSON、本地数组或 Mock 作为业务数据源。
2. 前端隐藏按钮不等于权限；所有写接口必须在服务端校验角色、按钮权限、门店和数据范围。
3. 不复制旧 ERP 真实客户、财务、健康记录作为测试数据；只采集结构、选项、规则和经负责人明确授权的主数据。
4. 当前工作区有大量未提交改动，不得执行 `git reset --hard`、`git clean` 或覆盖式回退。
5. 每完成一个页面，必须同时核验顶部工具栏、查询区、下拉选项、列顺序、表单/弹窗、联动、错误提示、权限和真实 API。

## 10. 权限迁移必须遵守的事实

旧 ERP 权限不是简单的“角色看哪些菜单”，而是：

```text
用户
→ 一个或多个角色
→ Web 菜单 / App 菜单
→ 页面按钮
→ 角色 + navId + 部门的数据范围
```

新系统已经保留：

- 原角色 ID；
- 原用户 ID；
- Web/App 来源；
- `navId`；
- 按钮 ID；
- 同名不同 ID 角色；
- 禁用账号；
- 一人多角色。

权限编码示例：

```text
LEGACY.WEB.N{navId}.B{buttonId}
LEGACY.APP.N{navId}.B{buttonId}
CUSTOMER.CREATE
SALES.APPROVE
FINANCE.APPROVE
ROOM.EXECUTE
```

新模块接入权限时必须：

1. 路由设置 `meta.permissions` 或 `meta.legacyNavId`；

5. 部门/本人范围只有在正向样本核验后才启用；
