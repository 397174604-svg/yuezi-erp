# 优惠券字段与编号规则

更新时间：2026-07-31

## 结论

- 原 ERP 已采集“数据字典”页面，共 123 类、693 项；但现有资料没有找到甲方确认的“优惠券编号生成规则”。
- 当前优惠券类型来自前端业务配置，不是数据库数据字典动态下发。正式上线后应由管理员维护数据字典，前端只读取启用项。
- 编号不再允许业务员手填，统一由系统生成，避免重复、空格、中文和跨门店冲突。

## 当前编号规则

| 对象 | 当前规则 | 来源 | 是否甲方确认 |
| --- | --- | --- | --- |
| 优惠券模板 | `YHQ-{数据库模板ID，6位补零}`，示例 `YHQ-000123` | 本项目后端实现 | 否 |
| 客户优惠券 | `YH-{年月日时分秒}-{4位随机码}`，示例 `YH-20260731143020-A1B2` | 本项目后端实现 | 否 |

编号一经生成不得编辑。数据库主键仍使用数字 ID，展示编号只作为业务检索和单据引用。甲方若要求包含门店码、券种码、年度流水或重置周期，需要另行确认后再调整。

## 本轮字段限制

| 字段 | 前端限制 | 后端限制 |
| --- | --- | --- |
| 客户姓名 | 必填，最多 30 字 | 必须匹配当前门店已有客户，最多 30 字 |
| 手机号 | 只能输入数字，最多 11 位 | 必须符合中国大陆手机号 `1[3-9]` 开头、共 11 位 |
| 优惠券名称 | 必填，最多 50 字 | 必填，最多 50 字 |
| 优惠金额 | 0.01–1,000,000，最多 2 位小数 | 同前端 |
| 模板发行数量 | 1–100,000 的整数 | 不得小于已发放数量 |
| 单客户限领 | 1–100 的整数 | 不得超过模板发行数量 |
| 单次发放数量 | 1–100 的整数 | 同时校验模板剩余量和客户累计限领量 |
| 有效期 | 1–3,650 天 | 起止日期必须有效，结束日不得早于开始日或今天 |
| 核销金额 | 0.01–1,000,000 | 不得超过优惠券剩余金额 |
| 关联业务单号 | 必填，最多 64 字 | 必填，最多 64 字 |
| 备注/说明 | 最多 500 字 | 同前端，并写入不可修改的操作审计记录 |

## 真实数据库运行说明

- 正式本地模式：`.env.mvp` / `.env.api`，`VUE_APP_ENABLE_MOCK=false`，业务数据写入 MySQL。
- Mock 不删除，只用于前端开发和断网演示；正式验收、上线包和数据库验收不得使用 Mock。
- 数据库迁移 `V20260731_020__coupon_redemption_and_validation.sql` 增加优惠券名称持久化与核销权限。
- 2026-07-31 已生成双店脱敏测试数据：每店 2 个客户、1 份已审核合同、1 个优惠券模板和 1 张客户券；中心店客户券已执行 100 元部分核销，供页面验收状态、金额、业务单号和操作流水。
- 客户建档、线索新增、优惠管理、优惠券模板、分发及核销中的手机号字段统一为仅数字、最多 11 位；保存时由前端和 API 同时校验大陆手机号格式，不能依靠绕过页面写入非法号码。
- 测试数据均带 `LOCAL_DEMO_SEED` 标记，可通过 `scripts/cleanup_local_demo_data.py` 精确清理，不会清空业务表或误删后续真实数据。

## 待甲方确认

1. 优惠券模板号和客户券号是否需要带门店代码。
2. 编号是否按年/月重新起号，作废编号是否允许再次使用。
3. 优惠券类型、消费类型和适用范围由总部统一还是各门店可维护。
4. “核销”权限最终授予销售经理、财务、前台收银中的哪些角色。
5. 模板分发后是否必须二次审核；当前系统对手工新增优惠券要求审核，模板直接分发默认已通过。
