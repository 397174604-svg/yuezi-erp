# 奇德芬芳 ERP：MySQL 员工与角色权限设计

> 日期：2026-07-25  
> 数据库：MySQL 5.7 / `yuezi`  
> 数据来源：建设路店、黄河路店员工花名册，以及原 ERP 四类账号的只读权限核验

## 2. 当前角色设计为什么不合理

原 ERP 的账号权限验证显示：

- 销售账号同时可见财务、客房、月嫂、膳食、仓存、商城、风控和报表等大范围菜单。
- 产康账号可见客户、销售、财务、客房、仓存和商城。
- 客房账号可见客户、护理、产康、月嫂、膳食、仓存、商城和风控。
- 非管理员账号仍能看到跨门店选择和部分财务/欠款信息。

这说明原权限把“岗位职责、管理职责、审批权限、跨部门协作、数据范围”揉进了一个角色，容易产生：

1. 同岗位人员因个人配置不同而权限漂移；
2. 能看菜单但不清楚能看哪家门店、哪个部门、哪些字段；
3. 普通员工获得审批、删除或跨店权限；
4. 调岗后旧权限难以及时回收；
5. 手机号、身份证号、金额等敏感字段缺少单独控制。

## 3. 新权限模型

权限不再直接挂在人或部门上，而分为六层：

1. **员工与账号分离**：`staff` 是人事档案，`user_accounts` 是登录身份；员工可以没有账号。
2. **基础岗位角色**：销售顾问、护理人员、产康师、客房管家、膳食员工等。
3. **管理角色**：销售经理、护理主任、产康经理、客房经理、膳食经理等，可与岗位角色叠加。
4. **特殊能力**：审核、删除、导出、打印、分配、执行等按操作单独授权，不从“能看页面”推导。
5. **数据范围**：本人、部门、本门店、全部门店；按模块分别设置。
6. **字段权限与临时委托**：手机号、身份证号、金额等可隐藏或掩码；请假代理、临时审批通过带起止时间的委托记录实现。

## 4. MySQL 表职责

| 表 | 作用 |
|---|---|
| `departments` | 门店下的部门树 |
| `positions` | 部门内岗位与管理岗标识 |
| `staff` | 完整当前员工主档；直接包含手机号、身份证原始值、地址、紧急联系人、工资卡号、合同和复核状态 |
| `staff_private` | 与主表同步的明文扩展资料，保留给字段权限和兼容接口使用 |
| `staff_roster_records` | 原花名册 94 条在职与 62 条离职来源记录，保留全部原始列及复核状态 |
| `user_accounts` | 登录名、密码哈希、锁定状态和默认门店 |
| `roles` | 岗位、管理、系统角色 |
| `permissions` | 模块与查看/查询/新增/编辑/删除/审核/导出/打印/分配/执行动作 |
| `role_permissions` | 角色允许的具体动作 |
| `user_roles` | 账号叠加角色与生效时间 |
| `user_stores` | 账号允许进入的门店 |
| `role_data_scopes` | 每个角色在每个模块的数据范围 |
| `field_permissions` | 敏感字段的可见、掩码、可编辑规则 |
| `access_delegations` | 有起止时间、原因和审批人的临时权限委托 |

## 5. 首批角色基线

本次建立系统管理员、总经理、人事主管、财务专员、销售经理/顾问、护理主任/护理人员、产康经理/产康师、客房经理/管家、膳食经理/员工、企划专员、仓库管理员、美容师、月嫂主管/月嫂共 19 个规范角色。

权限采用保守基线：

- 普通岗位默认只处理本人或本部门数据。
- 部门经理默认只能跨本部门、不能跨门店。
- 审核和删除不会因为“属于某部门”而自动获得。
- 系统管理员拥有全局能力；总经理以查看、查询、审核、导出和打印为主。
- 员工账号必须经过人工身份绑定和密码重置后才创建，避免把旧系统弱密码带入新系统。
