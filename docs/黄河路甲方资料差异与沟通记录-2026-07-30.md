# 黄河路甲方资料差异与沟通记录

- 建档日期：2026-07-30
- 适用范围：奇德芬芳月子会所 Web ERP
- 本批资料归属：以黄河路轻奢店为主，涉及中心店的既有资料仅用于差异对照
- 维护原则：未取得甲方书面确认的字段不作为正式经营制度；账号、密码等敏感信息不写入代码和项目文档

## 一、先给结论

1. 本批资料确认：**黄河路套餐体系不能复制中心店套餐体系**。两店的套餐名称、价格结构、房型绑定方式均不同，必须按门店建立独立套餐目录。
2. 黄河路本批确认出 7 组套餐，每组都有 28、35、42、56 天档位；资料同时给出了房型描述、照护内容、赠送服务、赠品和产康项目。
3. 智能排房应增加“门店 → 套餐版本 → 套餐允许房型 → 日期可用性”的硬过滤。该项已于 2026-07-30 完成本地联调，推荐排序只在通过硬过滤的房间中进行。
4. 本轮修复前黄河路 `VIP999` 被写成“两室二厅”；现已依据甲方聊天和总统套餐资料更正为“三房三厅（总统套）”。
5. 本轮修复前其余 23 间房被统一写成“一房一厅（修复套餐）”；现已拆分为物理房型“一房一厅”和独立的套餐允许范围（修复、修复7+21、修养）。
6. 产康表格和 Word 文档适合作为后续“服务项目、预约时长、耗材、标准操作、员工培训”的原始资料，不应阻塞当前客户—合同—收款—订房—入住主链上线。
7. 多份产康资料包含医疗化、疗效化和营销化表述，还有错命名、重复工作表。未经甲方负责人、专业人员及合规审核，不应直接作为正式 SOP 或对客话术上线。
8. 截图显示黄河路仍在使用共享部门账号和明文密码。正式上线前必须改为员工个人账号、门店和角色授权、首次登录改密及操作审计。

## 六、智能排房必须采用的门店与套餐规则

### P0 硬性过滤

```text
当前门店
  → 只显示该门店已生效套餐
  → 选择套餐版本及入住天数
  → 只保留套餐允许的物理房型
  → 排除维修、脏房、员工占用和日期冲突
  → 校验合同、收款及锁房资格
  → 进入推荐排序
```

任何一项硬性条件不满足，都不能仅靠“推荐分高”进入候选。

### P0 推荐排序

1. 全程同房且覆盖完整入住区间；
2. 与套餐房型完全匹配；
3. 客户确认的楼层、朝向、特殊需求；
4. 尽量减少未来房态碎片；
5. 清洁/维修缓冲充足；
6. 无连续房时才显示换房备选，是否允许换房及最多次数仍需甲方确认。

### 建议的数据关系

```text
门店
  ├─ 房型
  │   └─ 房间
  └─ 套餐
      ├─ 套餐版本（28/35/42/56天、价格、有效期）
      ├─ 允许房型
      └─ 权益明细（服务、次数、赠品、产康项目）
```

房型是物理属性，套餐是销售商品，二者不能继续混用一个字段。

## 七、岗位、账号和菜单差异

### 已取得的信息

- 黄河路现有业务至少涉及销售、产康、客房、财务四类部门操作。
- 截图中的账号以共享部门账号形式存在，并直接展示明文密码。
- 黄河路反馈膳食部没有使用 ERP。
- 黄河路反馈未设置或未使用面点师、勤杂工、企划、保安、司机、保洁洗衣等岗位。

### 对正式 ERP 的处理

- 不删除全系统的膳食、企划、司机、保洁等能力，因为中心店和以后门店可能仍需要。
- 按门店配置“启用模块、启用岗位、可见菜单”，黄河路未使用的岗位在黄河路隐藏即可。
- 所有共享账号改为员工个人账号；部门用于授权分组，不再作为多人共用登录身份。
- 财务登记与审核原则上分权；销售、产康、客房只能操作本门店和职责范围内的数据。
- 初始账号必须强制改密，密码不得出现在聊天记录、代码、Mock 数据、MD、日志或截图附件中。
- 对不存在的岗位仍需甲方说明职责由谁承担，例如接车、安保、保洁、洗衣、活动策划是否外包或由其他岗位兼任。
