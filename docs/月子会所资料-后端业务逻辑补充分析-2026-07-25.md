# 月子会所资料对后端业务逻辑的补充分析

日期：2026-07-25  
资料范围：`C:\Users\39717\Desktop\月子会所系统\月子会所资料`  
结论：**帮助很大**。这些资料不仅能补充页面字段，还能确定套餐权益、入退所协同、护理与客房执行、产康耗材、品控整改等核心业务规则。

本分析只提取业务结构、状态、规则和时效要求；不复制客户、员工、健康、联系方式等真实明细。

## 1. 资料价值分级

| 资料 | 后端价值 | 可确认的业务事实 |
| --- | --- | --- |
| 入所服务全流程 | 很高 | 签约后建服务群、入所前准备、资料核验、缴余款与押金、妈妈/宝宝双评估、跨部门服务、离所准备和离所后延续服务 |
| 护理部主任一日流程 | 很高 | 排班、交接、查房、重点客户优先、异常上报、护理记录检查、跨部门协同、培训考核 |
| 客房主管一日流程 | 很高 | 房间准备、入住物品交接、保洁、布草、洗衣、维修、满意度、物料领退和房态核验 |
| 套餐项目 PDF | 很高 | 套餐、房型、入住天数、服务次数、每日/每周/按需频次、赠品数量、可选项目约束 |
| 产康销售政策 | 很高 | 价格本、疗程、项目组合、选项组、赠送、互斥优惠、业绩和提成规则 |
| 产品配料表 | 很高 | 服务项目步骤与物料、标准用量、计量单位，能够形成服务执行到库存消耗的闭环 |
| 产康操作标准与话术 | 很高 | 项目版本、步骤、阶段、评估、禁忌、测量、前后影像、复评、员工培训与授权 |
| 部门检查标准 | 很高 | 品控标准、检查项、扣分、证据、整改、时限、部门得分和绩效联动 |
| 房间安排 | 中高 | 楼层、房间、房型、空间用途及套餐销售映射 |
| 会议纪要 | 中高 | 移动端优先、房态和经营预测、客户标签、权限边界、库存成本、积分与品控方向 |

| 员工花名册 | 有限且敏感 | 仅能用于确认员工主数据字段；本轮扫描件未做 OCR，也未提取个人信息 |

## 2. 新增的完整业务主链路

资料把现有“客户 → 合同 → 收款 → 订房 → 入住”扩展为可执行闭环：

```text
客户/线索
  → 合同版本与套餐快照
  → 应收、收款、押金
  → 订房及入住计划
  → 入所前资料清单与房间准备
  → 入住登记
  → 妈妈/宝宝双评估
  → 护理、膳食、产康、客房任务自动展开
  → 服务执行与耗材确认
  → 库存流水、权益耗用、成本归集
  → 满意度、异常、投诉及整改
  → 离所前评估和结算
  → 退房、离所、售后回访
```

建议增加统一的客户住店生命周期：

```text
SIGNED
→ PRE_ADMISSION
→ ROOM_READY
→ ADMITTED
→ IN_HOUSE
→ PRE_CHECKOUT
→ CHECKED_OUT
→ SETTLED
→ AFTERCARE
```

状态必须由业务事件推动并写入历史表，不能只在客户表保存一个当前状态文本。

## 3. 套餐、价格与权益模型

套餐资料证明，“套餐”不是一张只有名称和价格的表。它至少同时受套餐版本、房型、入住天数、门店和生效日期影响，且包含不同频次、赠品和可选项目。

### 3.1 建议表

```text
sale_price_book
sale_price_item
sale_package
sale_package_version
sale_package_duration
sale_package_entitlement
sale_package_choice_group
sale_package_choice_item
sale_package_goods
sale_promotion
sale_promotion_condition
sale_promotion_benefit
sale_promotion_exclusion
sale_commission_policy
sale_commission_rule
member_entitlement_account
member_entitlement_ledger
```

### 3.2 关键字段

`sale_package_entitlement`：

```text
package_version_id
service_project_id
frequency_type       -- ONCE / COUNT / DAILY / WEEKLY / ON_DEMAND
quantity
period_days
body_part_rule
choice_group_id
replaceable
valid_from_offset
valid_to_offset
```

`sale_package_choice_group`：

```text
group_name
min_select
max_select
allow_repeat
selection_deadline
```

合同签署时必须把套餐、权益、价格、赠品和选择结果保存为不可变快照。之后价格政策更新不能改变历史合同。

### 3.3 需要程序执行的规则

- 套餐天数决定服务次数和赠品数量。
- “任选 N 项”使用选择组校验，不使用备注文本。
- 项目是否可替换、优惠是否可叠加、赠送是否计业绩都必须数据化。
- 项目权益使用独立流水，支持套餐内、套餐外、额外购和项目卡四种来源。
- 退款按原权益和原收款分摊逆向冲销，不能直接修改剩余次数。

## 4. 入所、在住与离所协同

### 4.1 入所资料和房间准备

```text
stay_admission_plan
stay_document_requirement
stay_document_submission
stay_readiness_checklist
stay_readiness_result
stay_deposit
stay_access_card
stay_welcome_task
```

入所资料应配置为版本化清单，支持必填、有效期、附件、审核状态和缺失原因。房间准备也应采用清单实例，覆盖清洁消毒、设备、温度、热水、用品、餐食和套餐专属物资。

### 4.2 妈妈和宝宝双主体

合同客户、入住住客、妈妈档案和宝宝档案不能混成一张客户表：

```text
crm_customer
room_stay
care_mother_profile
care_baby_profile
care_guardian_relation
```

一份入住可以关联一位妈妈、一个或多个宝宝及陪住家属。护理评估、护理计划和健康记录通过 `subject_type + subject_id` 关联具体对象。

### 4.3 离所闭环

```text
stay_checkout_plan
stay_checkout_checklist
care_discharge_assessment
room_item_return
room_damage_charge
fin_checkout_settlement
crm_aftercare_plan
```

离所前 5～7 天生成准备任务；退房和财务结账必须是两个独立状态，以支持“已退房未结账”。

## 5. 护理执行和交接模型

资料确认护理中心应从“记录表集合”升级为按班次驱动的任务中心：

```text
care_shift
care_roster
care_handover
care_handover_item
care_round
care_round_observation
care_plan
care_plan_item
care_task
care_task_assignment
care_execution
care_issue
care_escalation
care_correction
```

关键规则：

- 新入住和重点客户提高查房优先级与频次。
- 夜间查房按配置频次生成任务，并检测超时。
- 妈妈与宝宝的观察项分别记录，不能只保存一段综合备注。
- 每班交接只带出新增、未完成、异常和重点观察项。
- 记录修正采用追加更正，禁止覆盖原执行事实。
- 跨部门问题生成协同工单并保留责任部门、处理时限和关闭证据。

## 6. 产康标准、执行与库存消耗

操作标准和配料表证明，产康服务需要“标准版本 → 执行实例 → 实际耗材”三层模型。

### 6.1 标准层

```text
svc_project
svc_project_variant
svc_protocol
svc_protocol_version
svc_protocol_phase
svc_protocol_step
svc_protocol_material
svc_measurement_definition
svc_contraindication
svc_required_certification
```

### 6.2 执行层

```text
svc_booking
svc_assignment
svc_execution
svc_execution_step
svc_execution_measurement
svc_execution_material
svc_before_after_media
svc_consent
svc_usage
```

### 6.3 库存联动

```text
服务确认完成
  → 按标准版本生成预计耗材
  → 执行人确认实际数量与批次
  → 写入 svc_execution_material
  → 生成 inv_stock_transaction
  → 回写项目实际成本
  → 进入门店/部门/项目毛利报表
```

产品配料中的 `ml`、`g`、支、片、套等单位必须进入统一计量单位表，一种物料一行；禁止把“各 10”“0.5G”等混合文本直接用于扣库存。

高风险或隐私项目还需要禁忌核验、知情确认、影像访问权限和敏感数据访问日志。

## 7. 品控、扣分与整改闭环

部门检查标准不是普通 Excel 报表，适合建设为独立质量管理模块：

```text
qc_standard
qc_standard_version
qc_standard_item
qc_inspection_plan
qc_inspection
qc_inspection_result
qc_evidence
qc_issue
qc_rectification
qc_recheck
qc_score
qc_employee_point_ledger
```

标准、检查结果和整改必须分表：

- 标准版本保存检查项、权重、扣分值、适用部门和生效期。
- 检查结果保存符合/不符合/不适用及现场证据。
- 不符合自动生成问题单、责任人、整改期限和复查任务。
- 分数按部门、门店和月份汇总；进入绩效前保留确认与申诉状态。
- 能从系统事实判断的规则自动检测，例如护理任务超时、房间准备超时、维修超时、库存盘点未完成。

资料中可直接配置为 SLA 的例子：

- 房间在入住前完成准备，退房后限时完成清洁。
- 报修限时响应，无法当日完成时必须给出预计完成时间。
- 护理夜间查房不得超过规定间隔。
- 满意度在入住后的固定天数生成任务。
- 膳食留样、餐具消毒、送餐时间窗和禁忌校验均留痕。

## 9. 员工培训、认证与可执行权限

产康操作资料同时具有培训和考核属性，因此员工是否能执行某项目不能只靠菜单权限：

```text
hr_training_course
hr_training_session
hr_exam
hr_exam_item
hr_exam_result
hr_certification
hr_employee_certification
svc_employee_project_authorization
```

项目授权应包含证书、考核结果、生效/失效日期和授权门店。预约分配时同时校验员工班次、房间/设备、项目授权和客户权益。

## 10. 会议纪要带来的架构约束

- 当前阶段优先模块化单体和移动端执行，避免过早拆分微服务。
- 房态、在住客户、护理、膳食、产康共用统一“在住客户上下文”。
- 管理层可看全局，部门负责人默认只看本部门；健康、财务和隐私项目再叠加字段权限。
- 客户标签必须有计算依据、版本和更新时间，不能只有人工标签名称。
- 经营看板需要入住率、未来占用、收入预测、项目耗用、物料成本和部门绩效。
- 系统落地必须减少重复录入；能从入住、权益或任务推导的字段不再要求员工手填。

## 11. 不建议直接导入的内容

- 员工花名册和真实客户/健康资料：先定义字段、授权、加密和脱敏规则，再经正式迁移流程导入。
- 操作话术全文：应经业务、医疗和合规审核后作为版本化知识内容发布，不应硬编码在页面。
- 图片和宣传资料：进入对象存储与内容资产表，只保存元数据和授权信息。
- Excel 中的合并单元格、自由文本用量和人工颜色：必须清洗为结构化数据后再入库。

## 12. 推荐实施顺序

1. 先补套餐版本、价格本、权益账户、选择组和合同快照。
2. 建立入所/离所清单、房间准备和双主体评估。
3. 建立护理班次任务、交接、异常升级和跨部门工单。
4. 建立产康标准版本、执行步骤、实际耗材和库存流水。
5. 建立品控标准、检查、整改、复查和计分。
6. 最后导入经清洗和审批的主数据，并完成金额、权益、房态、库存和权限对账。
